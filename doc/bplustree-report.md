SQLite나 외부 DB·패키지를 사용하지 않는다. 기존 CLI, CSV 스키마와 검증/skip 정책, 카테고리·예산·반복 규칙 기능을 유지한다. `transactions.jsonl`은 append-only이며 수정도 끝에 추가한다. `transactions.idx`는 기존 `<QQ` 16바이트 구조이고 id `N`의 슬롯은 `(N-1)*16`이다. 삭제 슬롯과 최대 발급 id를 compact·마이그레이션에서도 보존한다.

이전 날짜 항목과 삭제된 거래 항목은 **기존처럼 남겨 두고** 현재 슬롯·실제 날짜와 맞지 않으면 조회에서 제외한다. B+Tree의 물리 삭제/재균형은 추가하지 않았으며 기존 `compact`가 stale 항목을 제거한다. 따라서 여기서 N은 살아있는 거래 수가 아니라 compact 전 인덱스 키 수다.

### 먼저 읽는 용어·약어 설명

| 표기 | 원문 또는 뜻 | 이 프로그램에서 하는 일 |
|---|---|---|
| B+Tree | B+ 트리 | 여러 갈래로 내려가는 정렬 인덱스. 실제 조회 키는 leaf에 있고, internal은 어느 자식으로 갈지 안내한다. 여기서 `BPT`는 `+`를 Plus의 `P`로 표기한 프로젝트 내부 줄임말이다. |
| WAL | **Write-Ahead Log**, 선행 기록 로그 | 본 인덱스를 바꾸기 **전에** 복구에 필요한 내용을 먼저 저장하는 파일이다. 이 구현은 변경 후 페이지 전체 바이트를 보관한다. |
| redo | 재적용, 다시 하기 | WAL에 들어 있는 변경 후 페이지를 정해진 위치에 다시 써서 인덱스 갱신을 끝낸다. |
| undo | 되돌리기 | 거래번호 슬롯의 변경 전 바이트와 파일 길이를 복원해 미완료 거래를 취소한다. 날짜 WAL의 redo와 역할이 다르다. |
| COW / Copy-on-Write | 쓰기 시 복사 | 기존 페이지 대신 새 페이지에 변경을 기록하고 참조를 교체하는 방식이다. 검토한 대안이며 현재 구현은 페이지 WAL을 사용한다. |
| UUID | **Universally Unique Identifier**, 범용 고유 식별자 | 인덱스 파일을 새로 만들 때 부여하는 16바이트 식별자다. 현재 파일과 WAL이 같은 인덱스에 속하는지 대조한다. 거래번호가 아니다. |
| CRC32 | **Cyclic Redundancy Check, 32-bit**, 32비트 순환 중복 검사 | 페이지 바이트에서 계산하는 4바이트 검사값이다. 저장된 값과 다시 계산한 값이 다르면 부분 쓰기나 우발적 손상을 의심한다. |
| SHA-256 | **Secure Hash Algorithm, 256-bit**, 256비트 해시 알고리즘 | WAL 전체 및 슬롯 undo 기록의 본문에서 32바이트 해시를 계산한다. 복구 기록이 완전한지 확인한 후에만 적용한다. |
| JSONL | **JavaScript Object Notation Lines** | 한 줄에 JSON 객체 하나를 저장하는 텍스트 형식이다. 거래 원본은 `transactions.jsonl`에 남는다. |
| CSV | **Comma-Separated Values**, 쉼표 구분 값 | 사용자가 표 데이터를 가져오고 내보내는 파일 형식이다. 내부 B+Tree 파일 형식과는 별개다. |
| CLI | **Command-Line Interface**, 명령줄 인터페이스 | `python -m budget_app ...`로 실행하는 기존 사용자 명령이다. |
| id / ID | **Identifier**, 식별자 | `tx_id`는 거래번호, `page_id`는 페이지번호다. 이름이 비슷해도 서로 다른 번호다. |
| root / internal / leaf | 뿌리 / 내부 / 잎 노드 | root는 검색 시작점, internal은 분기 안내, leaf는 실제 복합 키 보관소다. |
| ordinal | 날짜 일련번호 | `0001-01-01`을 1로 세는 날짜 정수다. 날짜 문자열보다 작고 날짜 간 대소 비교가 쉽다. |
| offset | 바이트 위치 | 파일 시작부터 몇 바이트 떨어져 있는지를 나타낸다. 예를 들어 페이지번호 3의 위치는 `3 * page_size`다. |
| subtree / separator | 하위 트리 / 분기 기준 키 | 어떤 노드 아래의 전체 가지와, 좌우 가지를 구분하는 키다. 이 구현의 separator는 오른쪽 subtree의 최소 키다. |
| cache / dirty page | 캐시 / 변경된 페이지 | 캐시는 읽어 둔 페이지, dirty page는 메모리에서 바뀌어 아직 파일에 반영해야 하는 페이지다. |
| after-image | 변경 후의 전체 모습 | 명령 이름이나 차이만 저장하는 대신, 변경 후 페이지 전체 바이트를 WAL에 저장한다는 뜻이다. |
| commit / rollback | 완료 확정 / 취소 복원 | 복구 기준으로 작업을 끝낸 상태와, 미완료 작업을 이전 상태로 돌리는 동작이다. 인덱스 작업의 commit과 거래 자체의 commit은 구분한다. |
| stale / orphan / legacy | 더 이상 유효하지 않음 / 참조되지 않음 / 이전 형식 | 이전 날짜 키는 stale, 어떤 유효 슬롯도 가리키지 않는 JSONL 줄은 orphan, 기존 정렬 배열은 legacy다. |
| compact / migration | 압축 정리 / 형식 이행 | compact는 유효 데이터만 다시 저장하고, migration은 같은 거래를 유지하면서 저장 형식을 바꾼다. |

`flush()`는 Python의 쓰기 버퍼에 있던 내용을 운영체제로 보내는 작업이다. `fsync()`는 **file synchronization**의 의미로, 운영체제에 해당 파일의 변경을 저장 장치에 반영하도록 요청한다. 따라서 `flush()`만으로 장애 복구에 필요한 확정을 대신하지 않는다. 파일 이름을 바꾸거나 지운 결과는 디렉터리 자체의 변경이므로 파일뿐 아니라 부모 디렉터리에도 `fsync()`를 요청한다. 여기서 “확정”은 운영체제·파일시스템·장치가 이 요청을 준수한다는 전제다.

“원자적 rename”은 이름 교체가 관찰상 이전 파일 또는 완성된 새 파일 중 하나로 보인다는 뜻이다. 그 이름 교체가 전원 차단 후에도 유지되도록 요청하는 작업은 별도의 디렉터리 fsync다. 두 성질을 같은 것으로 보지 않는다.

## 2. 바이너리 파일 구조

모든 수치는 little-endian이다. 기본 페이지 크기는 4096바이트이고 page id `P`는 `P*page_size`에 위치한다. 설정한 페이지 크기는 헤더에 저장하므로 재시작 때 자동 인식한다. 지원 크기는 256~65536의 2의 거듭제곱이다. 페이지 끝 4바이트는 앞부분 전체(패딩 포함)의 CRC32다.

### `struct.Struct(...)`를 읽는 방법

`struct`는 Python 정수와 `bytes`를 정해진 크기의 바이너리 데이터로 바꾸는 표준 라이브러리다. `struct.Struct(형식문자열)`은 같은 배치를 반복 사용할 수 있도록 형식과 크기를 준비한 객체다. 이 객체 자체가 파일을 만들거나 쓰지는 않는다.

- `pack(...)`: 값을 바이너리 `bytes`로 만든다. 실제 파일 기록은 별도의 `fp.write(...)`가 한다.
- `unpack(raw)`: 정확히 그 구조 크기인 바이트를 읽어 Python 값들의 튜플로 돌려준다.
- `unpack_from(raw, offset)`: 더 큰 버퍼의 지정 위치에서 구조 하나를 해석한다.
- `iter_unpack(raw)`: 같은 구조가 여러 번 반복된 바이트에서 항목을 차례대로 꺼낸다.
- `.size`: 해당 구조가 차지하는 바이트 수다. 페이지 전체 크기와는 다를 수 있다.

실제 메타데이터 형식은 **`struct.Struct("<8sII16sQQQQQQ")`**다. 각 기호는 다음 뜻이다.

| 기호 | 의미 | 크기·범위 | 이 헤더에서 대응하는 값 |
|---|---|---|---|
| `<` | little-endian, 표준 크기, 자동 정렬 패딩 없음 | 자체 저장 바이트 없음 | 모든 숫자의 바이트 순서를 고정 |
| `8s` | 길이 8의 바이트 문자열 하나 | 8바이트 | `b"DATEBPT1"` |
| 첫 `I` | unsigned int, 부호 없는 정수 | 4바이트, 0~4,294,967,295 | 파일 형식 버전 |
| 둘째 `I` | 위와 같은 정수 | 4바이트 | 페이지 크기 |
| `16s` | 길이 16의 바이트 문자열 하나 | 16바이트 | UUID 원시 바이트 |
| 첫 `Q` | unsigned long long, 부호 없는 정수 | 8바이트, 0~18,446,744,073,709,551,615 | 실제 root 페이지번호 |
| 둘째 `Q` | 위와 같은 정수 | 8바이트 | 전체 페이지 수 |
| 셋째 `Q` | 위와 같은 정수 | 8바이트 | 전체 키 수 |
| 넷째 `Q` | 위와 같은 정수 | 8바이트 | 첫 leaf 페이지번호 |
| 다섯째 `Q` | 위와 같은 정수 | 8바이트 | 마지막 leaf 페이지번호 |
| 여섯째 `Q` | 위와 같은 정수 | 8바이트 | 세대 번호 |

`8s`는 `s` 항목 8개가 아니라 **8바이트 문자열 한 항목**이다. 따라서 이 형식의 `pack`에는 총 10개 값을 전달한다. `8s`는 입력이 짧으면 0으로 채우고 길면 잘라 저장하므로, 코드에서 magic을 정확히 8바이트로 정해 혼동을 피한다. `16s`에도 문자열 형태 UUID가 아니라 `uuid.uuid4().bytes`를 넣는다.

크기 계산은 `8 + 4 + 4 + 16 + (8 * 6) = 80`바이트다. `<`를 사용하므로 실행 컴퓨터에 따라 필드 사이에 임의의 정렬 공백이 들어가지 않는다. 뒤에서 페이지 크기에 맞춰 넣는 0 패딩은 프로그램이 **명시적으로 추가하는 별도 공간**이다.

요청에 적힌 **`struct.Struct("<8sIII16sQQQQQQ")`는 다른 배치**다. `I`가 하나 더 있으므로 4바이트 정수 필드가 3개이고 총 `8 + 4*3 + 16 + 8*6 = 84`바이트다. 이 경우 UUID 시작 위치는 16이 아니라 20, root 위치는 32가 아니라 36이 된다. 추가 `I`가 무엇을 의미할지는 형식 문자열만으로 알 수 없고 별도 설계가 필요하다. 현재 코드에는 그 세 번째 정수 필드가 없으므로 보고서도 80바이트 형식을 기준으로 설명하며 파일 포맷을 임의 변경하지 않는다.

예를 들어 숫자 4096은 16진수로 `0x00001000`이고 `<I`로 저장한 바이트는 `00 10 00 00`이다. 사람이 쓰는 16진수 표기와 달리 낮은 자리 바이트가 먼저 나온다. 다음 코드를 실행하면 실제 배치와 크기를 직접 확인할 수 있다.

```python
import struct

header = struct.Struct("<8sII16sQQQQQQ")
raw = header.pack(b"DATEBPT1", 1, 4096, bytes(16), 1, 2, 0, 1, 1, 0)
assert header.size == 80
assert len(raw) == 80
assert raw[12:16].hex(" ") == "00 10 00 00"
assert header.unpack(raw)[2] == 4096
assert struct.calcsize("<8sIII16sQQQQQQ") == 84
# bytes(16)은 배치 설명을 위한 0 UUID다. 실제 파일은 uuid4로 식별자를 만든다.
```

같은 `<`와 `I`, `Q`, `s` 규칙은 아래 페이지·키·복구 기록에도 적용된다. `B`는 부호 없는 1바이트 정수, `H`는 부호 없는 2바이트 정수다. 날짜 키는 저장 바이트를 그대로 문자열처럼 정렬하지 않고, 숫자로 복원한 `(날짜, 거래번호)` 튜플을 비교한다. little-endian 바이트의 사전식 순서가 정수 순서와 같다는 가정을 하지 않는다.

### Root 메타데이터: page 0

`struct.Struct("<8sII16sQQQQQQ")`, 고정 헤더 80바이트.

| 오프셋 | 크기 | 필드 |
|---:|---:|---|
| 0 | 8 | magic `DATEBPT1` |
| 8 | 4 | 버전 `1` |
| 12 | 4 | 페이지 크기 |
| 16 | 16 | 파일 UUID: 다른 파일의 WAL 재적용 방지 |
| 32 | 8 | 실제 root page id |
| 40 | 8 | 메타데이터를 포함한 전체 페이지 수 |
| 48 | 8 | 전체 키 수 (stale 포함) |
| 56 | 8 | 첫 leaf page id |
| 64 | 8 | 마지막 leaf page id |
| 72 | 8 | WAL 트랜잭션 세대 번호 |
| 80~4091 | 4012 | 0 패딩 |
| 4092 | 4 | CRC32 |

실제 root는 작은 트리에서는 leaf, 커진 트리에서는 internal이다. 각 노드의 root 플래그와 page 0의 root id가 일치하는지 검사한다. 초기 파일은 메타데이터 1개와 빈 root leaf 1개로 8192바이트다.

### 이름과 필드 크기를 이렇게 정한 이유

**magic은 파일 종류를 식별하는 고정 서명**이다. 암호나 특수 명령이 아니라 파일 첫 바이트를 읽었을 때 “이 파서로 읽을 파일이 맞는가”를 빠르게 확인하는 표식이다. 확장자가 같은 옛 정렬 배열과 새 B+Tree를 구분하는 데도 사용한다. 다음 이름은 외부 DB 표준이 아니라 이 프로젝트에서 정한 규칙이다.

| magic | 이름을 구성한 방식 | 바이트 수를 선택한 이유 |
|---|---|---|
| `DATEBPT1` | `DATE`는 날짜 인덱스, `BPT`는 B+Tree, `1`은 첫 번째 파일 형식 계열 | ASCII 문자 8개로 용도와 형식 계열을 함께 표시한다. 짧은 단일 문자보다 다른 데이터와 구별하기 쉽고, 비용도 고정 8바이트다. |
| `BPTP` | `BPT` + `P`(Page) | 각 페이지가 B+Tree 노드인지 확인하는 4바이트 표식이다. 페이지마다 반복하므로 파일 서명보다 짧게 잡았다. |
| `BPTWAL01` | `BPT` + `WAL` + `01`(첫 복구 기록 형식) | 본 인덱스 파일과 복구 파일을 혼동하지 않도록 8바이트로 별도 표시한다. |
| `TXUNDO01` | `TX`(Transaction, 거래) + `UNDO` + `01` | 날짜 페이지 redo가 아니라 거래번호 슬롯 undo 파일임을 나타내는 8바이트 표식이다. |

`b"DATEBPT1"`의 앞 `b`는 Python의 **bytes 리터럴**이라는 표시다. `D` 같은 ASCII 문자 자체가 각각 1바이트로 저장된다. 예를 들어 이 magic의 16진수 바이트는 `44 41 54 45 42 50 54 31`이다. 보고서에서 보기 쉽게 쓴 문자열과 디스크에 저장한 실제 바이트를 구분해야 한다.

다음은 메타데이터의 각 항목을 별도로 저장한 이유와 크기 선택 이유다.

| 항목 | 별도로 저장하는 이유 | 이 크기를 선택한 이유·한계 |
|---|---|---|
| 버전 `I`, 4바이트 | 같은 계열에서도 읽기 방식이 달라질 수 있으므로 지원 버전인지 숫자로 검사한다. 현재 값은 1이다. | 1바이트로도 현재 값은 충분하지만 다른 설정 정수와 같은 명확한 표준 32비트 필드로 정했다. CPU의 자동 정렬 때문에 반드시 4바이트여야 하는 것은 아니다. |
| 페이지 크기 `I`, 4바이트 | 페이지 주소 계산, CRC 위치와 키 수 계산에 필요하다. 재실행 때 생성 당시 크기를 알아야 한다. | 지원 최댓값 65536은 2바이트 unsigned의 최대 65535를 넘으므로 4바이트를 사용한다. 저장 표현 범위가 넓어도 구현이 허용하는 값은 256~65536의 2의 거듭제곱뿐이다. |
| 파일 UUID `16s`, 16바이트 | 같은 이름으로 새 인덱스를 만든 뒤 예전 WAL이 남았을 때 서로 다른 파일임을 알아낸다. | UUID는 128비트=16바이트다. 하이픈 포함 36문자 문자열보다 작게 원시 바이트로 저장한다. `uuid4`를 사용하며 절대 중복 불가능한 인증 정보라는 뜻은 아니다. |
| root 페이지번호 `Q`, 8바이트 | root split 후 새 root 위치를 page 0 한 곳에서 찾는다. | 페이지번호는 음수가 필요 없어 unsigned로 정했다. 32비트 페이지번호의 한계에 포맷이 일찍 묶이지 않도록 64비트를 쓴다. 값은 바이트 offset이 아니라 페이지번호다. |
| 전체 페이지 수 `Q`, 8바이트 | 주소 유효 범위, 실제 파일 길이, 다음 새 페이지번호를 결정한다. | 페이지번호와 같은 64비트 범위를 사용한다. `pages`는 메타데이터도 포함하므로 유효 노드번호는 `1 <= page_id < pages`다. 필드 표현 범위와 실제 운영체제·파일시스템의 최대 파일 크기는 별개다. |
| 전체 키 수 `Q`, 8바이트 | 파일을 모두 읽지 않고 `count()`를 처리하고 순위 조회 범위를 정한다. | 키 수는 페이지 수보다 훨씬 커질 수 있으므로 64비트로 통일했다. 수정 전 날짜나 미완료 키가 남을 수 있어 살아있는 거래 수와 같다고 보장하지 않는다. |
| 첫 leaf / 마지막 leaf, 각각 `Q` 8바이트 | 전체 오름차순·역순 조회를 시작할 때 root부터 끝까지 찾아가는 작업을 생략한다. | 다른 페이지 참조와 같은 64비트 페이지번호다. 작은 트리에서는 둘 다 root leaf인 1을 가리킨다. |
| 세대 번호 `Q`, 8바이트 | 페이지 WAL 갱신 때 변경 세대를 기록해 파일 상태를 살펴보기 쉽게 한다. rebuild는 새 UUID와 세대 0에서 시작한다. | 갱신 횟수가 커져도 쉽게 넘치지 않도록 64비트다. **현재 코드는 이 값을 비교해 오래된 WAL을 판정하지 않는다.** WAL 적용 대상 검사는 UUID와 형식·체크섬을 사용한다. |
| 0 패딩, 기본 4012바이트 | 작은 메타데이터도 다른 페이지와 같은 4096바이트 단위로 둬 주소 계산을 단순하게 한다. | `4096 - 80 - 4 = 4012`다. 현재는 모두 0이며 CRC 계산에 포함한다. 예약 공간이 있다는 이유만으로 새 필드를 추가해도 되는 것은 아니고 포맷 호환성 설계가 필요하다. |
| CRC32 `I`, 4바이트 | 페이지가 완전하게 읽히고 저장됐는지 검사한다. | 검사 결과가 32비트이므로 4바이트다. 작은 크기와 빠른 계산을 위한 선택이다. 충돌 가능성이 있으며 오류 정정 코드나 암호 인증 수단은 아니다. 복구할 원본 바이트는 WAL/원본 거래 파일에 있다. |

magic의 `1`과 별도 `VERSION=1`은 의도적으로 겹치는 정보다. magic은 파일 종류와 첫 형식 계열을 눈으로 구분하기 위한 것이고, 별도 버전 필드는 숫자로 읽기 지원 여부를 검사하기 위한 것이다. 현재 파서는 두 값 모두 정확히 맞아야 읽는다. 버전 숫자만 올리면 구형 코드가 자동으로 새 포맷을 읽게 되는 것은 아니다.

**4096바이트를 기본으로 둔 이유**는 원래 요구사항을 따르면서, 흔히 쓰이는 4KiB 단위로 한 번에 여러 키를 읽고 쓰기 위해서다. 1KiB=1024바이트이므로 4KiB=4096바이트다. 페이지가 작으면 한 페이지의 키가 줄어 트리가 깊어지고, 너무 크면 단건 작업에서도 더 많은 바이트를 처리한다. 4096은 이 둘의 절충이며 모든 운영체제·디스크에서 가장 빠르거나 한 번에 원자적으로 저장되는 크기라는 뜻은 아니다. 장애 안전성은 페이지 크기가 아니라 WAL·fsync·체크섬·복구 순서가 담당한다.

256바이트 같은 작은 크기는 테스트에서 분할을 적은 데이터로 여러 번 일으키는 데 유용하다. 2의 거듭제곱은 페이지 단위를 일정하게 유지하는 이 구현의 규칙이며, 임의의 양수 크기에서도 B+Tree가 원리상 불가능하다는 뜻은 아니다.

### Internal / Leaf 공통 헤더

`struct.Struct("<4sBBHQQQ")`, 32바이트.

| 오프셋 | 크기 | 필드 |
|---:|---:|---|
| 0 | 4 | magic `BPTP` |
| 4 | 1 | 종류: leaf=1, internal=2 |
| 5 | 1 | 실제 root면 1 |
| 6 | 2 | 키 수 |
| 8 | 8 | 이전 leaf id (internal은 0) |
| 16 | 8 | 다음 leaf id (internal은 0) |
| 24 | 8 | 해당 노드 아래 전체 키 수 |

`<4sBBHQQQ`의 크기는 `4 + 1 + 1 + 2 + 8*3 = 32`바이트다. 각 필드의 선택 이유는 다음과 같다.

- **종류 `B` 1바이트**: 현재 leaf=1, internal=2 두 종류만 필요하다. 다른 크기의 정수를 쓸 필요가 없어 1바이트로 둔다.
- **root 플래그 `B` 1바이트**: 참/거짓은 1비트로도 표현되지만 struct가 직접 다루는 1바이트 정수로 명확하게 기록한다. 현재 값은 0 또는 1이며 다른 비트 의미는 정의하지 않았다. root id와 교차 검사하는 보조 정보다.
- **키 수 `H` 2바이트**: 범위는 0~65535다. 지원하는 가장 큰 65536바이트 페이지에서도 leaf 키가 최대 5458개이므로 충분하다. 전체 트리 키 수가 아니라 **이 페이지의 키 수**이므로 8바이트가 필요하지 않다.
- **prev/next 각각 `Q` 8바이트**: 다른 페이지 참조와 동일한 크기다. leaf 연결에서 0은 “이전/다음 없음”이다. 메타데이터가 page 0이므로 실제 leaf 번호와 충돌하지 않는다. internal에서는 연결 목록을 쓰지 않아 둘 다 0이다.
- **하위 키 수 `Q` 8바이트**: leaf에서는 이 페이지 키 수와 같고, internal에서는 모든 자식의 키 수 합계다. internal 아래에 수많은 페이지가 있을 수 있으므로 `H`보다 넓은 64비트를 사용한다.

Leaf 본문은 `<IQ` 키의 반복이다. 날짜는 `date.toordinal()` unsigned 32-bit, 거래번호는 unsigned 64-bit다. 기본 페이지에는 최대 **338개 키**가 들어간다. `(날짜, id)`를 튜플 비교하므로 같은 날짜도 거래번호 순서대로 정렬되고 id의 상위 비트가 잘리지 않는다.

날짜 문자열 `YYYY-MM-DD`는 보통 10바이트지만 ordinal은 `<I` 4바이트면 충분하다. Python이 지원하는 마지막 날짜의 ordinal은 3,652,059로 32비트 범위 안에 들어간다. 3바이트 등으로 더 줄일 수도 있지만 struct에 없는 별도 인코딩을 만드는 대신 표준 4바이트 정수를 선택했다. 거래번호는 기존 `<QQ` 슬롯 방식의 식별자를 잘라 저장하지 않도록 `<Q` 8바이트다. 키 하나의 합계가 **12바이트**이므로 `(4096 - 32 - 4) // 12 = 338`개가 들어간다. 여기서 `//`는 나눗셈의 소수점을 버리는 Python 연산이다.

Internal 본문은 첫 자식의 `<QQ` (page id, 키 수) 16바이트 뒤에 `<IQQQ` (분기 날짜, 분기 id, 오른쪽 자식 id, 오른쪽 자식 키 수) 28바이트가 반복된다. 기본 페이지는 최대 **144개 분기 키 / 145개 자식**이다. 분기 키는 오른쪽 자식 subtree의 최소 키이며, 자식 키 수로 기존 `bisect_left` 순위 및 `iter_desc(lo, hi)` 인터페이스도 보존한다.

분기 키가 K개이면 자식은 K+1개다. 예를 들어 기준 키가 10, 20이면 자식은 “10 미만 / 10 이상 20 미만 / 20 이상” 세 개다. 그래서 첫 자식 `<QQ`를 한 번 저장하고, 이후 분기 키와 오른쪽 자식을 `<IQQQ`로 묶는다. `<QQ`는 `8+8=16`, `<IQQQ`는 `4+8+8+8=28`바이트이며, 용량은 `(4096 - 32 - 4 - 16) // 28 = 144`개다. 자식별 키 수 8바이트는 공간을 쓰지만, 앞쪽 자식들의 키 수를 더해 전체 순위를 구할 수 있어 기존 API를 유지하는 데 필요하다.

## 3. 삽입·페이지 분할 및 조회

1. root부터 internal 분기 키를 이진 탐색해 목표 leaf를 찾는다. 같은 키는 중복 추가하지 않는다.
2. leaf의 정렬된 위치에 삽입한다. 부모 경로의 자식 키 수를 갱신한다.
3. leaf가 339개 키가 되면 나눈다. 새 키가 leaf의 **맨 끝**에 들어가서 넘쳤으면 왼쪽 338개를 그대로 두고 새 키 하나만 새 오른쪽 leaf로 옮긴다. 날짜순 add나 정렬한 import는 늘 맨 끝에 붙으므로, 반반으로 나누면 왼쪽 절반이 다시 채워지지 않아 leaf가 평균 절반만 찬다. 그 밖의 경우는 169개/170개로 나눈다. 새 오른쪽 leaf의 최소 키를 부모에 복사한다. 새 leaf의 prev/next, 기존 leaf의 next, 기존 오른쪽 이웃의 prev를 함께 변경한다. 마지막 leaf가 바뀌면 메타데이터도 갱신한다.
4. internal이 145개 키가 되면 가운데 키를 부모로 승격하고 좌우에 72개 키/73개 자식을 둔다. 맨 오른쪽 자식이 나뉘어 넘친 경우에는 leaf와 같은 이유로 끝에서 두 번째 키를 승격해 왼쪽에 143개 키, 오른쪽에 키 1개·자식 2개를 둔다(분기 키 0개인 internal은 만들지 않는다). 부모가 넘치면 같은 과정을 위로 반복한다.
5. 기존 root가 분할되면 자식 2개를 갖는 새 internal root를 만들고 page 0의 root id를 바꾼다. 이 변경 전부가 하나의 WAL에 포함된다.
6. **일괄 생성**(`rebuild`, compact·재생성·큰 import에서 사용): 키를 하나씩 삽입하지 않는다. 오름차순 키로 leaf를 왼쪽부터 338개씩 꽉 채워 page 1부터 차례로 쓰고, 각 leaf의 (첫 키, 페이지 번호, 키 수)로 그 위층 internal을 자식 145개씩 만든다. root 하나가 남을 때까지 반복한다. 마지막 묶음에 자식이 하나뿐이면 앞 묶음에서 하나 가져온다. 정렬되지 않은 키는 거부한다(같은 키는 한 번만 둔다). 넣을 건수가 기존 키 이상인 import는 기존 키와 새 키를 `heapq.merge`로 합쳐 일괄 생성한다(`rebuild_merged`).

`iter_range(lower, upper, reverse=...)`는 `[lower, upper)` 범위를 한 번 내려가 찾은 leaf부터 연결 목록으로 읽는다. 저장소의 포함 종료 날짜는 `(종료일 ordinal + 1, 0)`으로 바꾸므로 날짜 `9999-12-31`도 넘치는 date 객체 없이 처리한다. 역순은 prev 링크를 이용한다. 키 기준 삽입/검색은 O(log N), K개 키 범위 조회는 O(log N + K)를 목표로 하며, 페이지 크기를 고정한 구현이다.

일반 단건 작업의 clean cache는 최대 64페이지이고, 바뀐 경로와 분할 이웃만 보관·기록한다. 범위 조회는 전체 인덱스를 메모리에 올리지 않는다. 여러 키를 넣는 `merge`는 바뀐 페이지가 256개(`MAX_DIRTY_PAGES`)를 넘으면 그때까지를 WAL 하나로 먼저 확정하므로 변경 페이지 메모리가 배치 크기와 무관하다(삽입 한 번이 바꾸는 페이지 수, 즉 2×높이+3개만큼은 넘을 수 있다). 묶음별로 확정하므로 날짜 인덱스의 원자성은 묶음 단위다. 거래의 존재는 슬롯과 import 기록이 정하므로 일부 묶음만 남아도 안전하다(상한을 4페이지로 낮춰 2,551번 강제 종료해 매번 트리가 온전함을 확인). 입력 키는 import·재생성 모두 건당 12바이트 배열(날짜 4 + id 8)에 모아 날짜별로 나눠 정렬하므로 이 부분은 배치 크기에 비례한다(100만 건 약 20MB). 디스크 외부 정렬은 구현하지 않았다.

## 4. 장애 복구와 파일 간 일관성

### 왜 WAL을 선택했는가

Copy-on-Write는 원래 페이지 보존에 유리하지만 양방향 leaf 링크의 버전과 복사 전파를 함께 관리해야 한다. 이 구현은 변경 페이지 after-image redo WAL을 사용해 root·부모·분할 leaf·이웃 링크를 같은 복구 단위로 묶는다.

WAL 헤더는 `<8sI16sQQ` 44바이트: magic `BPTWAL01`, 페이지 크기, 파일 UUID, 목표 페이지 수, 이미지 수다. 이후 `<Q page_id> + 전체 페이지 이미지`가 반복되고, 파일 끝의 SHA-256 32바이트가 WAL 전체 본문을 검증한다. 이미지 자체도 각 페이지의 CRC32로 검사한다.

### WAL의 필드 크기와 로그 길이 계산

| 필드 | 형식·크기 | 선택 이유 |
|---|---|---|
| WAL magic | `8s`, 8바이트 | 본 파일이나 슬롯 undo와 구별하는 고정 서명 |
| 페이지 크기 | `I`, 4바이트 | 본 파일의 헤더가 일부 손상돼도 각 after-image의 길이를 알기 위해 WAL에도 저장 |
| 파일 UUID | `16s`, 16바이트 | 같은 경로에 재생성된 다른 인덱스에 WAL을 적용하지 않도록 본 파일과 대조 |
| 목표 페이지 수 | `Q`, 8바이트 | split로 파일이 늘어나는 경우 복구 후 정확한 파일 길이를 결정 |
| 이미지 수 | `Q`, 8바이트 | 로그가 다 기록됐는지 길이를 검사하고 몇 개 페이지를 읽을지 결정. 큰 배치도 표현할 수 있게 페이지 수와 같은 크기 사용 |
| 각 이미지의 페이지번호 | `Q`, 8바이트 | 이어지는 바이트를 어느 페이지 위치에 써야 하는지 지정 |
| 각 이미지 본문 | `page_size`바이트 | 페이지의 일부 변경 명령 대신 완성된 바이트 전체를 보관해 split·링크·root를 그대로 재현 |
| 전체 본문 해시 | SHA-256 원시 `digest`, 32바이트 | 헤더, 이미지 개수, 페이지번호, 모든 페이지 바이트를 함께 검사 |

따라서 전체 WAL 길이는 `44 + 이미지 수 * (8 + 페이지 크기) + 32`바이트다. 기본 페이지 이미지가 4개면 `44 + 4*4104 + 32 = 16492`바이트다. `digest()`는 256비트=32바이트를 반환한다. 사람이 보기 좋은 `hexdigest()`의 64자리 문자열을 저장하는 것은 아니다.

CRC32는 각 페이지 자체의 손상을 빠르게 확인하고, WAL 전체 SHA-256은 페이지번호와 헤더까지 포함한 복구 기록 한 묶음을 확인한다. 둘 모두 바이트 검증용이며 암호화하지 않는다. 현재 구현에는 비밀키 기반 인증도 없다. 검증 실패한 WAL을 추측해서 부분 적용하지 않고, 저장소 계층이 확정된 거래번호 인덱스와 JSONL을 기준으로 날짜 인덱스를 다시 만든다.

정상 순서:

1. 변경할 페이지를 메모리에서 완성한다. 본 인덱스는 아직 수정하지 않는다.
2. `.wal.tmp`에 WAL 전체를 쓰고 flush/fsync한다.
3. `.wal`로 원자 rename하고 디렉터리를 fsync한다.
4. 본 파일의 변경 노드들을 쓰고 **마지막에 page 0**을 쓴다.
5. 파일 길이를 확정하고 flush/fsync한다.
6. WAL을 지우고 디렉터리를 fsync한다.

재시작은 헤더를 읽기 **전에** WAL을 확인한다. WAL 길이·SHA-256·페이지 CRC·UUID·주소를 전부 확인한 뒤 전체 이미지를 다시 쓰고 fsync한다. 재적용 중 또 종료되어도 WAL이 남아 같은 내용을 반복 적용한다.

| 장애 지점 | 복구 결과 |
|---|---|
| WAL 임시 파일 작성 중 / publish 전 | 본 인덱스는 이전 상태, 임시 WAL 폐기 |
| WAL publish 후 / 페이지 쓰기 중 | WAL 전체 redo |
| leaf/internal split 또는 양방향 링크 일부 기록 후 | 모든 관련 페이지와 링크를 같은 WAL로 redo |
| root 메타데이터 일부만 기록됨 | WAL의 page 0 이미지로 복구 |
| 데이터 fsync 후 WAL 삭제 전 | 같은 이미지를 다시 적용해도 결과 동일 |
| WAL 자체가 손상되어 검증 불가 | 저장소가 확정된 idx+JSONL에서 날짜 인덱스 재생성 |
| WAL 없이 leaf가 손상됨 | CRC/구조 오류와 compact 안내. compact로 재생성 |

### 날짜 인덱스 완료와 거래 완료의 구분

날짜 WAL을 재적용했다고 거래 자체를 커밋하지 않는다. **거래의 존재·최신 버전·삭제 여부는 기존 `transactions.idx`가 결정한다.** JSONL이나 날짜 키만 보고 거래를 복원하면 삭제한 거래를 되살리거나 실패한 import를 부분 반영할 수 있으므로 그렇게 하지 않는다.

단일 add/update/delete는 `transactions.idx.slot-undo`에 원래 파일 길이와 원래 슬롯을 먼저 확정한다. `<8sQQ16s` 40바이트 헤더(magic `TXUNDO01`, 이전 길이, 거래번호, 이전 슬롯) + SHA-256 32바이트다. 슬롯 기록·fsync 뒤 undo 기록 삭제와 디렉터리 fsync를 마치면 거래 완료다. 기록이 남으면 add의 파일 길이 또는 update/delete의 원래 슬롯을 복구한다. 이 복구도 다시 종료되면 재실행할 수 있다.

이때 `<8sQQ16s`는 `8 + 8 + 8 + 16 = 40`바이트이고 해시를 더한 기록 하나는 **72바이트**다. 이전 파일 길이는 큰 JSONL의 크기가 아니라 **거래번호 인덱스 idx의 바이트 길이**다. add가 슬롯을 추가하다 중단되면 이 길이로 자르고, update/delete가 기존 슬롯을 덮다 중단되면 저장한 원래 16바이트를 해당 위치에 돌려쓴다. `16s`는 기존 슬롯 `<QQ`의 시작/끝 offset 8바이트씩을 해석하지 않고 그대로 보존하기 때문에 16바이트다. 새 add에는 이전 슬롯이 없으므로 16개의 0바이트를 넣고 이전 길이를 복구에 사용한다.

예를 들어 날짜 인덱스에 “TX-7을 2024-03-01 위치에 추가”하는 페이지 WAL이 확정돼도, TX-7 슬롯이 이전 JSONL 레코드를 가리키면 거래 수정은 아직 확정된 것이 아니다. 재시작 시 날짜 WAL은 redo할 수 있지만 미완료 슬롯은 undo한다. 조회는 TX-7의 실제 날짜와 다른 새 날짜 키를 건너뛴다. 이처럼 redo와 undo를 서로 다른 파일에 쓰는 이유는 날짜 색인은 재생성 가능한 보조 데이터이고, 거래번호 슬롯은 거래의 존재와 현재 버전을 결정하기 때문이다.

JSONL 기록 후 날짜 인덱스 실패 시 슬롯은 아직 바꾸지 않아 기존 거래가 유지된다. 새 로그 줄은 고아로 남아 compact에서 정리한다. 미완료 날짜 키는 슬롯 범위·삭제 상태·실제 날짜와 대조해 제외하므로 목록·검색·요약·export·recurring의 기존 동작이 유지된다.

시작 시 순서: 기존 compact 복구 → 기존 import 전체 rollback → 단일 슬롯 undo → 기존 부분 슬롯 정리 → 날짜 WAL redo/메타데이터 검사/필요 시 재생성 → 기존 카테고리 초기화다. import와 compact의 기존 완료 지점·재시작 정책은 유지한다. 카테고리 건수도 기존처럼 장애 시 실제보다 많게만 남긴다.

### 기존 인덱스 마이그레이션

기존 12바이트 배열을 발견하면 정확한 원본을 `.legacy.bak.tmp`에 복사·fsync하고 `.legacy.bak`로 rename·디렉터리 fsync한다. 그 다음 살아있는 거래만 idx+JSONL에서 읽어 `.build` B+Tree를 만들고 fsync한 뒤 원래 경로로 원자 교체한다. 이미 있는 최초 백업은 덮어쓰지 않는다.

백업 또는 빌드 중 실패하면 원래 배열은 그대로다. 교체 전 종료되면 다음 실행에 다시 마이그레이션하고, 교체 후 종료되면 완성된 B+Tree를 사용한다. 이 과정에서는 JSONL·거래번호 인덱스의 바이트나 id를 변경하지 않는다.

동일 data-dir의 동시 프로세스 실행은 기존처럼 지원하지 않는다. 복구 보장은 파일시스템이 fsync·원자 rename을 준수한다는 전제다. 실제 매체 고장, 모든 원본 파일의 손상, WAL 도입 전 이미 손상된 거래번호 슬롯은 날짜 인덱스만으로 복구할 수 없다.

함수 단위에서 1.6ms 느린 최신 날짜 추가는 명령 단위에서는 Python 시작 시간(약 0.08s)에 가려 차이가 보이지 않는다. 10만·30만 건 결과와 모든 명령은 README 5부에 있다.

처음 구현은 leaf를 늘 반반으로 나누고 rebuild도 키를 하나씩 삽입해, 100만 건에서 `date.idx` 20.7MB, compact 25.46s, import 325MB였다. 끝에 붙인 키 분할(3절 3·4번), 일괄 생성(3절 6번), 묶음 확정과 배열·정렬로 지금 수치가 됐다.

환경과 전체 수치는 [`bplustree-benchmark.json`](bplustree-benchmark.json)에 보존했다.

## 8. 소스코드를 읽는 순서

전체 코드를 처음부터 한 줄씩 읽기보다 파일 형식 → 검색 → 삽입 → 확정 → 재시작 순서로 따라가면 각 함수가 필요한 이유를 이해하기 쉽다. 핵심 함수와 처리 경계에 한국어 docstring(함수·클래스 첫 부분의 설명 문자열) 및 주석을 달았다.

| 순서 | 파일·코드 | 읽을 때 확인할 내용 |
|---|---|---|
| 1 | `bplustree.py`의 `META`, `PAGE_HEADER`, `KEY`, `CHILD`, `BRANCH` | 바이트를 어떤 순서와 크기로 기록하는지 본다. `Struct` 정의는 실제 파일 쓰기와 구별한다. |
| 2 | `_Meta.encode/decode`, `_Page.encode/decode` | 메모리 값을 바이트로 바꾸고, 읽을 때 길이·CRC·필드 범위를 검사하는 과정을 본다. |
| 3 | `_Session.read/save/new` | 디스크 페이지를 읽어 두는 캐시와 아직 확정하지 않은 dirty 페이지를 구분한다. `save()`는 즉시 디스크에 쓰는 함수가 아니다. |
| 4 | `_Session.find/select` | 키를 찾는 경우와 정렬 순위로 찾는 경우를 구분한다. `path`는 나중에 부모를 되짚는 경로다. |
| 5 | `DateIndex.iter_range`, `_iter_ranks` | 시작 leaf만 찾고 prev/next로 이동한다. 범위의 끝 `upper`/`hi`는 포함하지 않는다. |
| 6 | `DateIndex._insert`, `rebuild`, `_bulk_load` | leaf split에서는 키를 부모에 복사하고, internal split에서는 가운데 키를 부모로 승격하는 차이를 본다. 맨 끝에 붙인 키로 넘치면 한쪽으로 몰아 나누는 조건도 본다. 일괄 생성은 삽입 없이 leaf를 왼쪽부터 꽉 채워 쓴다. |
| 7 | `DateIndex._commit`, `_apply` | WAL 임시 저장 → 이름 확정 → 노드 기록 → 메타데이터 기록 → fsync → WAL 삭제의 순서를 본다. |
| 8 | `DateIndex.recover` | 어떤 페이지도 덮기 전에 WAL 전체를 검사하는 이유, 같은 이미지를 다시 써도 복구를 반복할 수 있는 이유를 본다. |
| 9 | `durability.py`의 `SlotUndo.prepare/commit/recover` | 거래번호 슬롯은 왜 redo가 아니라 이전 바이트로 undo하는지, 기록 삭제가 왜 거래 완료 시점인지 본다. |
| 10 | `repository.py`의 `ensure_files`, `append_transaction`, `update_transaction`, `delete_transaction`, `iter_latest_transactions` | JSONL·거래번호 인덱스·날짜 B+Tree를 조합하면서 실제 거래의 존재 여부를 판정하는 곳이다. |

예를 들어 새 거래를 저장하면 `append_transaction()` → JSONL append → `DateIndex.merge()` → `_insert()` → `_commit()` 순서로 날짜 키가 저장된다. 이후 `SlotUndo.prepare()` → 거래번호 슬롯 append → `SlotUndo.commit()`을 마쳐야 거래 자체가 완료된다. 종료 후 다시 실행하면 `ensure_files()`가 필요한 undo/redo를 처리한 뒤 목록을 읽는다.
